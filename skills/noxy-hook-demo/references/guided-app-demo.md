## Default production approach

1. **Make the app demo a guided explanation, not a sped-up screen tour.** Use short black-text-on-white captions that tell viewers what is useful at the same moment the corresponding action or outcome appears. No decorative title sequence or generic feature dump.
2. **Start at the meaningful action.** Cut gallery browsing, onboarding, settings, empty screens and most processing time. A purposeful jump cut from input to result is often clearer than retaining a fast spinner. Do not claim that edited footage demonstrates real processing latency.

   **When retention drops at the demo handoff, test an earlier payoff rather than another hook or cosmetic-only edit.** The user reported a drop after four seconds. Inspect when the actual result first appears, keep the hook fixed, compress setup to a few frames, and carry a short result-led caption across the action→result cut so viewers need not reread. A tested edit design uses 0.4s of meal photo then the native estimate at total-video 3.6s (previously 5.4s), with the real meal's approximate calories in the caption and a brief non-obscuring outline around the native value. Keep portion review, fox, totals and streak, but shorten dead time and use outcome/consistency language instead of feature narration. A shorter cut is a hypothesis; label the retention drop as user-reported and never claim improvement without follow-up analytics. Keep musical start/sync while trimming and fading the new ending. Recheck caption placement after rewriting: a second dashboard-caption line can obscure HP even when the previous one-line caption was safe.
3. **Open on the homepage, then show chat, and finish on streaks.** This is the user's explicit preferred demo order: homepage/fox → chat photo logging → actual calorie/macro estimate and portion review → meal logged/fox celebration → streaks last. Do not default to opening on the food photo or push the homepage behind chat. Keep one meal and its real values. Leave the homepage's fox, HP and daily totals unobstructed; a single caption line may be safer than two. Inspect the beginning and end of native homepage scrolling, not only a midpoint: a y=715 caption can cross the fox even when a later frame looks clear. 4. **Use conversational sentences, not feature labels.** User rejected the first caption treatment and asked for a closer match to the supplied videos. Avoid defaulting to tiny labels such as “calorie + macro estimates” or fragmented instruction copy. ## Retention self-critique

When asked to critique and fix retention, inspect the actual edit and quantify app reveal, first native useful result, and promised emotional payoff separately. Diagnose the hook-to-proof connection and reading burden, not just total duration. A clean export can still be a weak story. Make the hook's promise visible in the demo, and use a setup/action/payoff when supported by native footage. Remove redundant narration and disconnected shots. The user rejected the brief uncaptioned post-celebration homepage as random: go directly from celebration to streaks, with native totals still visible within the retained screens. Shorten reaction/setup time only when the new hook remains readable, and preserve the complete fox celebration rather than truncating the payoff. Re-sync music to the changed reveal and verify actual final frames. Report before/after edit timings as editing measurements, never proof of improved retention. Label multi-variable recuts honestly; they cannot isolate the cause of any later performance change. Save case-specific results in the project handoff, not as a universally winning formula.

## Verification and persistence

For stream-copy revisions, MP4 concat can insert H.264 parameter sets into each segment's first packet, so packet hashes may differ even without re-encoding. Verify decoded frames as well as non-initial packet payloads and relative timestamps. When original segments mix full-range yuvj420p and limited-range yuv420p, normalize both sides to the same color range/pixel format before framemd5 comparison (`scale=in_range=auto:out_range=tv,format=yuv420p`); otherwise raw pixel hashes can disagree only because of representation. Describe this as normalized decoded-frame preservation rather than claiming every encoded packet is identical.

Persist the edit decision list, exact source ranges/speeds, text, caption bounds, geometry, source hashes and output metadata. Probe every final file for dimensions, SAR/DAR, fps and duration; fully decode it and inspect final frames for every caption/action/payoff. Deliver the actual playable MP4, preferably with a separate demo-only export, not merely a contact sheet.

Keep observed reference facts separate from editorial reasoning and user approval. These patterns plausibly improve clarity; no analytics here prove retention or conversion effects. The first reference-derived revision is a review draft, not a user-approved winner.
